# Test Baseline Maintenance

## 目标

让测试随代码与有效契约共同演进，而非只增不减。以**最小必要的测试维护成本**保障核心功能、稳定契约和关键回归风险；不以用例数量、代码行数或覆盖率数字作为唯一目标。

## 适用与边界

- 在功能开发、缺陷修复、重构、接口或协议变更、行为移除，以及专门的测试整理任务中使用。
- 只审查**变更影响范围内**的测试及其依赖；不借机大规模重构无关测试。
- 文档或格式等不影响行为与测试风险的修改，评估后可以不调整测试。
- 优先遵守项目已有的测试框架、命名约定、质量门禁和合规要求；本 Skill 不要求引入新框架、辅助脚本或覆盖率阈值。

## 工作流

### 1. 确认有效契约与变更影响

- 从需求、设计文档、公共接口、现有代码和测试中识别：哪些行为应保持，哪些明确改变，哪些正式废弃。
- **以预期行为为准，区分重构与契约变更**：现有测试不是业务正确性的唯一依据。纯重构应保持有效行为及测试断言不变，不得为适配意外行为变化而改写预期；只有需求或契约明确改变，或原测试与已确认的要求冲突时，才调整相关断言。需求不明确时，不自行将实现现状视为新契约。
- 标出受影响的核心流程、边界条件、错误处理、安全权限、数据一致性、并发/故障恢复、兼容性及历史缺陷风险；不相关项无需展开。

### 2. 新增测试前先审查现有测试

- 定位受影响的测试文件、场景、断言、公共夹具与 Mock；必要时参考相关调用方和集成测试。
- 判断各测试保护的有效行为，以及是否失效、重复、脆弱、过度绑定实现或存在覆盖缺口。
- 环境允许时，先运行受影响的现有测试建立基线；若无法运行，记录原因，不能推断其已通过。
- **新增长期测试的准入检查**：明确其保护的有效行为或独立失败模式、具体回归后果与现有覆盖缺口，确认断言依据稳定契约且能区分正确与错误行为，并权衡维护与执行成本；高风险但覆盖不确定时继续核查，不因无法量化风险而放弃保护。
- 代码发生修改、增加分支或覆盖率数字变化，本身均不足以构成新增测试的理由；能通过调整现有测试补足保障时，不新建冗余用例或测试文件。

### 3. 选择最小必要的维护动作

按以下判断处理，不要求每次变更都执行全部动作：

| 判断 | 动作 |
| --- | --- |
| 测试仍保护有效契约且稳定 | **保留**，无需为了整理而改动 |
| 明确的业务契约或接口发生变化 | **更新**相关测试与断言，保留仍有效的行为保障 |
| 多项测试真正重复且合并不损害可读性、隔离性和故障定位 | **整合**重复场景或夹具 |
| 测试只覆盖已废弃行为，且不再保护任何当前约束或风险 | **清理**；删除前确认不存在独有的关键回归保障 |
| 新增有效行为、修复缺陷或发现重要且未覆盖的风险 | **补充**最小充分的新测试，优先复用现有测试结构 |

- 对**已移除行为的一次性验证**可使用临时测试，完成后不纳入长期基线；若行为移除形成新的禁止性约束、安全要求或重要回归风险，应保留相应长期测试。
- 针对同一行为选择覆盖关键等价类、边界条件与独立失败模式的**最小充分测试集**，避免同质输入、重复断言、冗余 Mock 和仅为覆盖率复制低价值场景；不得为减少用例数而合并不同失败模式的测试，真实历史缺陷应保留必要保护。
- 如测试迁移、合并或删除，需确认它原先独有的有效断言和风险保护已保留、替代或确实不再适用。

### 4. 根据风险选择测试层级与范围

- 优先保护核心用户/业务路径、对外契约、关键边界、数据完整性与权限安全、历史高风险缺陷；基础库还应保护 API、协议与系统不变量。
- 测试文件与场景应优先围绕功能行为、接口契约、组件职责及系统不变量组织，遵循项目现有约定；当测试结构存在明显碎片化、职责混杂或重复时，适度整理，同时保持测试的独立性、可读性与故障定位能力。
- 在合适的层级验证：单元测试用于局部规则，集成/契约测试用于真实交互，端到端测试用于少量关键流程。以项目实际架构和已有测试体系为准。
- 测试应确定、可理解、可维护；避免无必要的内部方法断言、过度 Mock、全局状态依赖及复杂辅助抽象。
- 对风险很低且已被有效测试覆盖的修改，允许**不新增测试**。

### 5. 执行验证并如实报告

- 根据影响范围运行受影响的测试及必要的相邻回归测试；高风险或跨模块变更在条件允许时扩大至集成或全量测试。
- 发现失败先区分：预期契约变更、真实回归、测试失效、环境问题；不可直接通过删测、跳过或弱化断言消除失败。
- **新增测试价值与检错能力自检**：确认新用例弥补了现有覆盖缺口且断言能够识别目标错误。重要缺陷修复在安全可行时验证测试对原缺陷先失败、修复后通过；其他高价值用例可按需以局部故障注入或变异测试验证检错能力，不对所有测试强制执行。缺乏独立价值的用例应合并、调整或移除，不削弱重要回归保障。
- 结束时简要说明：`保留 / 更新 / 整合 / 清理 / 新增`了哪些相关测试及原因；执行的验证命令和结果；未执行的测试、已知限制与剩余风险。

## 不可违反的约束

1. 不得为了让测试通过而随意修改正确的业务逻辑、降低有效断言强度、删除有效测试或隐藏失败。
2. 不得以“测试精简”为由削弱关键回归保障；删除前先证明已废弃或存在等效且可靠的覆盖。
3. 不强制每次修改都新增、删除或重组测试；仅在有明确维护价值时调整。
4. 不凭空声称测试已经通过、行为未变或覆盖充分；无法验证时明确披露。
5. 不将一次性临时验证代码误纳入持续测试基线；监管、审计或项目要求留存的验证记录除外。

## 输出方式

完成开发任务时，在常规变更说明中附加**简短的测试维护摘要**，而不是生成独立的大型报告：

- **测试维护**：保留/更新/整合/清理/新增的关键处理及理由；新增测试简述独立回归价值与现有覆盖缺口，无变更则说明现有覆盖为何足够。
- **验证结果**：实际执行的命令、通过/失败/未执行情况。
- **残余风险**：尚未验证的受影响场景（如无则省略）。
