# Test Baseline Maintenance

## 目标与边界

让测试随有效契约演进，以最小必要的维护成本保护关键回归风险；不以用例数量、代码行数或覆盖率数字作为唯一目标。

- 仅审查变更影响范围内的测试及其依赖，按需调整，不扩大到无关整理；不影响行为或测试风险的文档、格式修改可不调整测试。
- 遵循项目已有的测试框架、命名约定、质量门禁和留存要求；本 Skill 不要求引入新框架、辅助脚本或覆盖率阈值。

## 工作流

### 1. 确认有效契约与变更影响

- 结合需求、项目文档、公共接口、现有代码和测试，确认应保持、改变或废弃的行为；现有实现与测试均不是业务正确性的唯一依据。
- 纯重构保持有效行为和断言语义；仅在需求或契约明确改变，或原测试与已确认要求冲突时调整预期，不得将意外行为变化视为新契约。
- 识别受影响的核心流程、公共契约、**系统不变量**、边界与错误处理、安全权限、数据一致性、并发与恢复、兼容性及历史缺陷风险；不相关项无需展开。

### 2. 审查现有测试与覆盖缺口

- 定位相关测试、夹具与 Mock，检查其有效保障、覆盖缺口，以及失效、重复、脆弱或过度绑定实现的问题。
- 环境允许时先运行相关测试建立基线；无法运行时记录原因，不推断其已经通过。
- 新增长期测试前，明确现有覆盖缺口、所保护的有效行为或独立失败模式及回归后果，确保断言依据稳定契约且能够识别目标错误，并权衡维护与执行成本；能补充现有测试时优先复用。
- 代码、分支或覆盖率变化本身不构成新增测试的理由；高风险但覆盖不确定时继续核查，不因无法量化风险而放弃保护。

### 3. 选择最小必要的维护动作

| 判断                     | 动作                                             |
| ------------------------ | ------------------------------------------------ |
| 测试仍保护有效契约且稳定 | **保留**                                         |
| 需求或契约明确改变       | **更新**相关测试与断言                           |
| 结构混杂或重复影响维护   | **整合**场景或夹具，保持可读性、隔离性与故障定位 |
| 测试已失效或冗余         | **清理**，先核实下述覆盖承接条件                 |
| 存在重要覆盖缺口         | **新增**最小充分的测试                           |

- 迁移、整合或删除前，确认原有独有断言与风险保障已保留、由可靠等效覆盖承接或不再适用；不得因减少数量而丢失独立失败模式或历史缺陷的有效保障。
- 行为移除的一次性验证可使用临时测试，完成后原则上不纳入长期测试基线；若形成新的禁止性约束、安全要求或重要回归风险，应保留相应长期测试。验证记录的留存按项目要求独立处理。
- 测试应围绕有效行为、公共契约、组件职责及系统不变量组织，避免过度依赖内部实现、冗余 Mock 和复杂辅助抽象。
- 新增时优先覆盖关键等价类、边界条件和独立失败模式，避免为同一风险添加大量相似输入、重复断言或低价值用例；不得为减少用例数而削弱不同失败模式的覆盖、隔离性和故障定位能力。

### 4. 选择验证范围并执行

- 依据风险选择能覆盖目标失败模式的测试层级，运行受影响及必要的相邻回归测试；跨模块真实交互优先采用集成验证，高风险变更按需扩大范围。
- 优先遵循项目已有的测试命令、配置、文档及 CI 质量门禁；没有明确约定时，根据项目结构选择适当的验证方式。
- 失败时先区分契约变更、真实回归、测试失效和环境问题；不得为消除失败而随意改变正确业务逻辑、弱化断言、删除或跳过有效测试、掩盖失败。
- 确认新增测试能够识别目标错误；重要缺陷修复在安全可行时验证测试对原缺陷先失败、修复后通过，其他高价值用例按需采用局部故障注入或变异测试。检错能力不足时调整用例。
- **新增后独立价值复核**：检查新用例是否确实提供现有测试未充分覆盖的回归保护；缺乏独立价值时调整、整合或移除，并遵守第 3 步的覆盖承接条件。

## 输出方式

在常规变更说明中简要交代，不另建报告：

- **测试维护**：关键动作及原因；新增测试说明覆盖缺口与独立价值，未调整测试说明原因。
- **验证结果**：实际执行的命令与结果、未执行项及原因；不得凭空声称测试通过、行为未变或覆盖充分。
- **残余风险**：已知覆盖缺口及尚未验证的受影响场景，无则省略。
